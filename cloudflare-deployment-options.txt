Deploying this app on Cloudflare — feasibility report
=======================================================

Context
-------
This Django app (currently deployed on Azure App Service via Daphne/ASGI, per
"ReadMe-Making SLA SCHEDULER WORK WITH AZURE.txt") was evaluated for possible
deployment on Cloudflare. This report covers all realistic approaches and
their tradeoffs.

Why this is non-trivial
------------------------
The app's architecture is a poor fit for Cloudflare's original serverless model:
- ASGI + Channels + Daphne, long-lived WebSocket connections (config/asgi.py)
  — Workers are short-lived, request/response.
- PostgreSQL with Postgres-specific features (ArrayField etc.) — Workers can't
  hold a normal TCP/psycopg connection pool the way a regular server can.
- Redis used as cache backend, rate limiting, and (in production) the Channels
  layer.
- Standalone long-running process: run_sla_scheduler / process_sla must run
  continuously, outside the request cycle.
- LibreOffice binary invoked as a subprocess for document conversion
  (documents_display app) — needs a real filesystem + native binary, not a
  V8 isolate.
- Cloudinary for production media storage (could be swapped, but that's a
  separate decision).

None of that runs in a plain Cloudflare Worker (V8 isolate, no subprocess
spawning, no arbitrary binaries, CPU-time-capped). So "deploy as
Workers/Pages" in the traditional sense is not viable without a major
rewrite (dropping Channels/WebSockets, dropping LibreOffice conversion,
rearchitecting the scheduler, moving off direct Postgres driver usage).

The options, ranked by realism
-------------------------------

OPTION A (recommended): Cloudflare as edge/CDN + security layer in front of
the existing host
------------------------------------------------------------------------------
Keep Django/Daphne running exactly where it runs today (Azure App Service, or
wherever it's hosted when scaling up — Azure Container Apps, a bigger App
Service plan, a VPS, etc.) and put Cloudflare in front as DNS + reverse
proxy. Nothing about the app's architecture changes; Cloudflare sits between
the internet and the existing origin.

What it involves, concretely:
1. DNS cutover: point the domain's nameservers (or just the relevant
   A/CNAME records) at Cloudflare, with the app's record "proxied" (orange-
   clouded) rather than "DNS only" (grey-clouded). This is what turns on all
   of Cloudflare's edge features for that hostname.
2. TLS: set SSL/TLS mode to "Full (strict)" — Cloudflare terminates TLS from
   the browser, then re-encrypts to the origin (Azure already provides a
   valid cert, so strict mode works without extra cert management). Enable
   "Always Use HTTPS" and HSTS at the edge (the app's own
   SecurityHeadersMiddleware and production HSTS settings in
   config/settings/production.py keep working underneath — Cloudflare adds a
   layer, doesn't replace it).
3. WebSocket passthrough: Cloudflare proxies WS connections to the origin by
   default (no config needed on paid or free plans for standard WS) —
   ws/notifications/ continues to hit Daphne through Cloudflare exactly as it
   does directly today. Verify after cutover since Channels' long-lived
   connections are worth a smoke test, but no code changes required.
4. Django settings changes needed: add Cloudflare's edge IP ranges awareness
   for real client IP — Cloudflare sends the true client IP in
   CF-Connecting-IP; Django needs USE_X_FORWARDED_FOR / trust of that header
   (or Cloudflare's True-Client-IP) wired into whatever currently reads
   request.META['REMOTE_ADDR'] (rate limiting, audit logs, ImpersonationLog,
   etc.), otherwise every request will appear to originate from Cloudflare's
   IPs. Also add the Cloudflare-fronted hostname to ALLOWED_HOSTS and
   CSRF_TRUSTED_ORIGINS if not already covering it (likely already fine
   since the domain doesn't change, just the proxy hop in front of it).
5. WAF / rate limiting / bot protection: Cloudflare's WAF can absorb generic
   attack traffic (SQLi/XSS patterns, credential stuffing on login) before it
   reaches Django at all — complements, doesn't replace, the app's own
   auth/rate-limiting.
6. Cloudflare Access (optional): zero-trust gate in front of sensitive paths
   (e.g. Django admin, documents_display internal review routes) requiring
   SSO/email verification before Cloudflare even forwards the request to
   origin — an extra layer beyond Django's own role-based permissions.
7. Caching: cache-control rules for static/ (CSS/JS/images) at the edge —
   Django's existing static file versioning/hashing (if using e.g.
   ManifestStaticFilesStorage) works well with aggressive edge caching since
   filenames change on content change. Avoid caching dynamic HTML/API
   responses (ticket data, dashboards) — configure Page Rules / Cache Rules
   to bypass cache for those paths, since none of this app's authenticated
   pages should be edge-cached.
8. Cloudflare R2 for media (optional, separate decision): R2 is S3-
   compatible, so it's a drop-in swap for whatever S3-compatible/Cloudinary
   storage backend is configured in config/settings/production.py (e.g. via
   django-storages) — mainly attractive for egress cost (R2 has no egress
   fees) rather than a technical requirement. Not needed to get the CDN/WAF
   benefits; can be done independently, later, or not at all.

Effort / risk:
- Effort: low — mostly DNS + settings + a few Django header/middleware
  tweaks, no architecture change, no rewrite of Channels/scheduler/
  LibreOffice/anything that made Option B risky.
- Risk: low — fully reversible (just repoint DNS back / set record to "DNS
  only" to bypass Cloudflare instantly if something misbehaves).
- Directly supports the upcoming scale-up: offloads static asset delivery
  and generic attack/bot traffic from the origin, so Django/Postgres/Redis
  capacity is spent on real application traffic — this is complementary to
  scaling the origin itself (bigger App Service plan, more Daphne workers,
  etc.), not a substitute for it.

OPTION B: Cloudflare Containers running the whole app as-is (Docker)
-----------------------------------------------------------------------
Cloudflare Containers (GA in 2025/2026) run arbitrary Docker images on
Cloudflare's edge, with WebSocket connections proxied automatically to the
container. This is the only Cloudflare product that could realistically host
the actual Daphne/Django process, LibreOffice binary, and the scheduler
process, essentially unchanged.
- Requires Workers Paid plan ($5/mo) + container usage billed per 10ms
  active.
- Caveat: Containers are designed for bursty, sleep-when-idle workloads —
  not ideal for an always-on Daphne WebSocket server or the
  run_sla_scheduler continuous polling process. Could work if the scheduler
  is redesigned to run as a Cloudflare Cron Trigger hitting process_sla on
  an interval (already a single-pass command, so this fits well) rather than
  the long-lived run_sla_scheduler loop.
- PostgreSQL: connect directly from the container (it's a real Docker
  container with normal networking) — Hyperdrive is a Workers-specific
  accelerator for JS/TS drivers and not needed/applicable here.
- Redis: no managed Redis on Cloudflare; would run Redis elsewhere (existing
  provider) or as a sidecar/separate container, connected over the network
  like today.
- Effort: medium-high (containerizing, adapting scheduler to Cron Triggers,
  persistent storage considerations since containers don't have durable
  local disks). Risk: medium — newer product, less proven for always-on
  stateful workloads than traditional PaaS/VPS.

Deep dive: Option B, given plans to scale up soon
---------------------------------------------------

How it actually works:
Cloudflare Containers are NOT a normal load-balanced fleet of replicas
behind an L7 balancer, which is the model this app currently gets from Azure
App Service. Instead:
- Each container instance is backed by a Durable Object (DO). A Worker
  script (@cloudflare/containers Container class) is what receives every
  HTTP/WS request and decides which DO/container instance to route it to.
- There is no built-in load balancer — you write (or use their minimal
  default) routing logic in the Worker: round-robin across a pool of
  instances, or a fixed mapping. This is a materially different scaling
  model than "add more replicas, put a load balancer in front," which is
  what App Service/most PaaS/VPS setups give you for free.
- Requests reach the container only via HTTP(S); raw TCP/UDP isn't exposed
  to end users. WebSocket upgrade requests are proxied through fine (Daphne
  handles WS over HTTP upgrade already, so no protocol issue there).
- All container disk is ephemeral — if an instance sleeps/restarts it gets a
  fresh disk. Cloudflare's own docs say persistent volumes are "not slated
  for the near future"; the workaround is FUSE-mounting to R2, which does
  not behave like real block storage.
- Cloudflare's own docs explicitly describe Containers as best for "bursty,
  edge-adjacent workloads that can sleep" — and explicitly NOT a drop-in
  replacement for an always-on PaaS when you need persistent disks,
  predictable monthly spend, or simple long-running services.

Changes required to run this app on it:
1. Containerize the app (Dockerfile bundling Django, Daphne, LibreOffice
   binary, deps) — moderate effort, mechanical.
2. Write a Worker router in front of the container pool (routing/health-
   checking/scaling logic that App Service currently gives for free).
3. Scheduler: replace the long-lived run_sla_scheduler loop with Cloudflare
   Cron Triggers calling process_sla (already a single-pass command) on an
   interval — needs a small adapter (e.g. an authenticated HTTP endpoint the
   cron Worker hits, similar in spirit to the existing Azure WebJob/
   scheduler.py pattern, since the same "no long-lived background loop"
   constraint applies).
4. Redis: no managed Redis on Cloudflare — keep it external (existing
   provider or a VM), reached over the network from the container. Latency
   depends on network path/colocation.
5. PostgreSQL: connect normally from inside the container (it's a real
   container with real networking) — Hyperdrive doesn't apply here, it's a
   Workers(JS)-specific accelerator, not usable from a Python/psycopg
   connection.
6. Any local-disk assumptions (LibreOffice temp conversion files, any file-
   based caching) need auditing — must not assume the disk survives a
   restart/sleep cycle. Production media already goes to Cloudinary, so that
   part is likely already fine; needs verifying nothing else touches local
   disk for anything other than a single request's temp lifetime.
7. Session/WS state: Channels already externalizes real-time state via the
   Redis channel layer, so horizontally-scaled Daphne processes work today.
   That pattern carries over, but now interacts with the DO-per-instance
   routing model, which needs load-testing to confirm no surprises (e.g., a
   client's WS connection pinned to one DO/instance while REST calls get
   routed elsewhere by the Worker's routing logic).

Runtime-risk assessment for an app that's about to scale up:
Given the priority of scaling up soon and avoiding runtime issues, Option B
carries real, above-average risk for that specific goal:
- No mature built-in load balancing — you own the routing correctness and
  failure handling in the Worker; a normal PaaS gives you this for free and
  it's proven at scale.
- Ephemeral disk is a permanent architectural constraint (not just current-
  limitation), so any future feature relying on local disk needs an R2/FUSE
  workaround with unproven performance.
- Cloudflare's own documentation says this product is not intended to
  replace an always-on PaaS for workloads needing predictable spend and
  simple long-running services — which describes this app (always-on WS
  server + continuous SLA tracking + admin/agent traffic) more than it
  describes a "bursty, sleep-when-idle" workload.
- It's a comparatively newer product (GA push with major limit increases as
  recently as Feb 2026) — less production track record than Azure App
  Service, Fly.io, Render, ECS, etc. for always-on stateful Django/ASGI apps
  at scale.
- Billing is per-10ms-active; for an always-on WS server this behaves more
  like always-on billing anyway, removing the main cost advantage
  Containers have for bursty workloads, while still carrying the
  architectural constraints above.

Bottom line: technically buildable, but for an app about to scale up in
production, Option B trades a proven, boring, load-balanced hosting model
(what it has today) for a newer platform whose own vendor documentation says
it isn't meant to replace exactly this kind of always-on workload. If
Cloudflare involvement matters strategically (e.g., cost, edge presence,
DDoS/WAF), recommend Option A now (Cloudflare in front of the existing/any
conventional host, R2 for media) and revisit Containers later once
persistent volumes and load-balancing primitives mature — rather than doing
the Option B migration right before a scale-up event.

OPTION C: Partial decomposition — static/frontend on Cloudflare Pages,
API/app elsewhere
---------------------------------------------------------------------------
Not a good fit here since this is a server-rendered Django app (templates,
not a decoupled SPA) — would require a significant frontend rewrite to
separate static assets from server-rendered pages. Mentioned for
completeness but not recommended.

OPTION D: Full rewrite onto native Workers (D1/Durable Objects/KV, no
Django)
---------------------------------------------------------------------------
Theoretically "deploy on Cloudflare" could mean re-platforming off Django
entirely onto Workers + D1 (SQLite-based) + Durable Objects (for WebSocket/
real-time state) + KV. This would mean abandoning Django/DRF, Postgres-
specific features, Channels, and rewriting the whole app in a Workers-
compatible runtime. Not realistic as a "deployment" — this is a rewrite, not
a migration. Included only so the theoretical ceiling of "fully on
Cloudflare" is documented.

Recommendation
---------------
Lead with Option A as the practical, low-risk move available today
(Cloudflare in front of the current/any host + R2 for media). Option B
(Containers) is the real path if the goal is literally "run the app itself
on Cloudflare," but given the imminent scale-up it carries meaningfully
higher risk today (see deep dive above). Options C and D are points on the
spectrum, not recommended.
